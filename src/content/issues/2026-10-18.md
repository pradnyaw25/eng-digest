Four posts, one move. Each one identifies the work that sits on the latency or throughput path and relocates it. Source control keeps state on the server instead of every client. D1 resolves routing without asking the database of record. Ad embeddings are computed before the request arrives. Agent output is checked before a human sees it.

---

## Anthropic stops treating git as a distributed system because its clients are always online

Anthropic's monorepo went from about 2,500 merges a day in May 2026 to over 30,000 by September. CI runs roughly 25 million checkouts a day, and the post estimates naive git fetching at that rate would move over 600 PB daily. Hundreds of mirrors, shallow clones and refreshed seeds bought time but became hard to operate. The team's observation is that git assumes offline, peer-to-peer work, while nearly every client here is an agent or a job with a network connection. Their system, Scion, keeps history, blame and merges on the server and has clients request only the trees and blobs they lack. Commits are changesets in a write-ahead log, derived data such as blame is computed from parents, and a ref update is a compare-and-swap on one row. A three-tier topology of node daemon, regional cache and authoritative server uses the same RPCs at each level.

The reported results are cache hit rates above 99% at each tier, infrastructure CPU and memory about 200x smaller than the mirror fleet, and CI gaining about 25% CPU capacity. Read the limits too. Scion is not a general git replacement and needs its own review, search and CI tooling. The team dropped merge queues with a global lock and relies on post-merge testing, accepting that concurrent changes can conflict. Seven engineers finished the migration in five months, which is a staffing number worth weighing before copying the approach.

## Cloudflare's D1 never sends a query through the control plane database

D1 backs each database with a SQLite-backed Durable Object, and AI-driven development now creates databases per user or per preview environment. Live databases grew about 15x in a year. Cloudflare splits the system into a data plane for queries, a control plane for provisioning and limits, and an asynchronous plane for analytics and billing. Queries resolve routing from Workers KV and fall back to Postgres replicas through Hyperdrive only on a miss. User bindings embed the routing information, and unique IDs rather than names avoid an extra lookup. Creation is a retry loop whose checkpoint is the Postgres write, and each Durable Object polls the control plane about every 30 seconds to repair partial creations and deletions.

The limit enforcement is the part to study. Usage deltas land in a table and a job aggregates them into per-account totals every second, which avoids row lock contention. Row-count limits flow through ClickHouse and reach Durable Objects as a flag in Quicksilver, so analytics load never touches Postgres. The stated cost is slower reaction to usage spikes and account-level caching that gives up per-database precision. Several flows are eventually consistent and depend on heartbeats to converge, so the design only works if every step is idempotent.

## Meta's Solaris precomputes ads embeddings and accepts that some will be stale

Meta's Generative Ads Model replaces separate prediction systems per surface and objective with one large model, and the post reports an 18.9% conversion improvement and 12% CTR improvement, both measured by Meta. The serving problem is that a very large model is too slow for an ad request. Solaris borrows from speculative decoding. It computes user-ad embeddings asynchronously for ad candidates likely to come up and delivers them on the serving path. When an exact embedding is missing, it falls back to the user's recent embeddings for the same ad groups or to embeddings from similar users. On the training side, Component Skip cut FLOPs by 43% with little quality loss, and model FLOPS utilization doubled to 20 to 25%.

The tradeoff is freshness for cost, and the post says plainly that coverage degrades rather than disappearing. Treat the headline gains with care, since they are self-reported and the scaling-law evidence partly comes from a lightweight model. A 20 to 25% MFU figure is also a reminder that recommender training still wastes most of the hardware. The reusable idea is the fallback ladder: define what the system serves when the precomputed value is absent before choosing what to precompute.

## Meta's Forum team counts only verified changes, not code volume

A small Meta team built Forum, a standalone app for deeper conversation in Facebook Groups, and reached core feature parity in eight weeks while working with an agent as a participant. Their success metric was changes that build, pass tests and survive review. The practices are concrete. Task completion requires automated tests and visual checks to pass. Agents inspect the live view hierarchy before editing, which sharply reduced edits to the wrong screen. Prototype code is compiled out of the production build rather than feature-gated. When an agent repeats a mistake more than twice, the correction is encoded as a rule. An agent-driven stress test found a memory issue, and fixing it roughly halved memory growth and page faults.

The post calls human-on-the-loop a target, not a finished state, and every shipped change still gets an engineer's sign-off. The sharper point is that automation is bounded by how far you trust your verifiers, and weak verification moves the bottleneck to review rather than removing it. Rebuilding some components instead of reusing them traded code reuse for agent throughput. The post gives few numbers beyond the eight weeks and the memory result, and its section on what did not work is in images, so the failures are not fully visible.
