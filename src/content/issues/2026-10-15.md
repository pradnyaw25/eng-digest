Each post this week traces a cost to an assumption that held in an earlier setting. Small socket
writes were harmless until an idle TCP window shrank. Cache bytes were portable under Postgres but
not MySQL. A short page looked like a cheap query. A health check that answered was taken as a
healthy GPU. The fixes are small once someone checks the assumption.

---

## ClickHouse removes a 32 ms stall caused by small writes and an idle TCP window

A ClickHouse customer saw simple SELECT queries take about 64 ms, twice the 32 ms round trip,
whenever a connection had been idle for 2 seconds or more. The cause sat between the protocol and
the kernel. After the result data, the Native protocol sends several small metadata packets before
EndOfStream, and with TCP_NODELAY each one became its own segment. After idle, Linux resets the
congestion window to its initial value, 8 segments in this setup, so the server ran out of window
and waited a full round trip for an ACK. The team reproduced it with network namespaces and a 32 ms
netem delay, then batched the metadata packets into one write. Server-to-client packets per run
fell from 50 to 25 and the tail dropped to about 1 ms.

The rejected options are worth reading. Disabling slow start after idle or raising initcwnd were
outside the customer's control, and TCP_CORK leaves batching to the kernel and is Linux-only. One
limit is noted: Progress packets are time-sensitive and cannot be held for batching.

[source →](https://clickhouse.com/blog/chasing-32ms-tail-latency-clickhouse)

## Cloudflare's 0.001% MySQL bug came from cache bytes assumed to be portable

Hyperdrive, Cloudflare's database connection pooler for Workers, made MySQL support generally
available after what the team calls about 20 bug fixes. The hardest one returned empty results on
roughly 0.001% of queries for the beta's largest MySQL customer, and only with caching on.
Hyperdrive splits each instance into a Client next to the Worker and an Endpoint near the database,
and the two share a cache when they run in the same data center. The Client cached the bytes it
wrote to the Worker, translated to the Worker driver's MySQL capabilities, while the Endpoint cached
bytes in Hyperdrive's own capabilities. A node reading the other's entry could send an early EOF or
hang. The trigger was a driver, mysql2, that does not support CLIENT_DEPRECATE_EOF.

The fix was to always cache one canonical encoding, after which client connection success reached
99.99%. The broader point is that the cache rule "store what you send" came from Postgres, where it
held. Any shared cache between nodes that negotiate different formats needs one canonical form.

[source →](https://blog.cloudflare.com/hyperdrive-mysql/)

## GitHub learns that a short page is not a cheap query

Tools rebuilt a repository's star history by paging through stargazer records, 100 per page,
keeping timestamps and discarding identities. For react/react, about 251,000 stars, that took about
2,511 requests. A pagination bug also counted every star on every request. In the week before
GitHub restricted stargazer lists to collaborators, nearly 37,000 of those count queries were
logged as slow, averaging nearly 3 seconds, and safeguards killed more than 1,000.

Aggregating into daily buckets and then paginating did not help, because the database still grouped
and sorted every star before LIMIT and OFFSET applied. The shipped endpoint turns each page into an
indexed date range, filters first, then counts. Each request returns up to 30 weeks of daily counts,
full history for react/react takes about 24 requests, and each star is read about once. The stated
limit is that a single week with very many stars can still make an expensive query.

[source →](https://github.blog/engineering/architecture-optimization/from-2500-requests-to-24-rebuilding-star-history-without-the-stargazers/)

## Netflix stops trusting GPU health checks that only prove the box is up

Netflix runs gang-scheduled training jobs across hundreds of GPUs for weeks, so one bad device or
network link stalls the run. Cloud instance checks and "driver responds" checks missed the real
failures: memory faults that appear only under load, network adapters with fewer links than
expected, and diagnostic tools that hang or quietly stop running. A node agent now checks every 30
seconds and fails closed when a tool times out. It falls back to kernel logs when the error reader
breaks and uses Netflix's own map of fatal error codes per GPU generation. Remediation is graded
from killing the job to resetting a GPU, rebooting, or replacing the machine, with a cap on how much
of a cluster can be disrupted at once.

Netflix reports more than 99.95% GPU node availability and job success up from about 98% to above
99.5%. The detail to copy is that a missing dependency now fails the check. One upgrade dropped a
binary, the check stopped running, and machines with the wrong adapter count shipped for days.

[source →](https://netflixtechblog.medium.com/reliable-gpu-compute-for-large-training-inference-jobs-d62b03a96d7a)

## Datadog decides which services are critical from its own postmortems

Datadog ran thousands of internal services under uniform deployment and SLO rules, and rollouts
across data centers got slower with every data center added. To decide which services deserve care, an
LLM read several hundred SEV-1 and SEV-2 postmortems and extracted the services involved, in under
a day for about $32. A second model checked those names against the service catalog. Incident
history is one signal among four. Error traces and paging monitors can raise a service's
criticality, near-zero traffic can only lower it, and owners can override the result with a reason.

The design is deliberately asymmetric. A false positive costs some caution, while a false negative
lets a critical service deploy fast, so the system prefers false positives. Consumers such as
dependency auto-merge choose how much confidence they need before automating. The post publishes no
accuracy figures, and it notes that a reliable service that has never failed is invisible to the
incident signal.

[source →](https://www.datadoghq.com/blog/how-datadog-defines-service-criticality-at-scale/)
