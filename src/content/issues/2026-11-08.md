Five posts, one question: when the system can't tell, which way does it fail? Cloudflare's planner resolves doubt into extra work. ClickHouse's failover resolves a failed fence into availability. GitHub narrows the part that needs agreement to a single operation. Meta stops one bad input from blocking everyone else, and Anthropic's memory write-up shows what a stale note costs when it is injected into every session.

---

## GitHub keeps consensus for the ref update and nothing else

GitHub's new Git storage design aims for at least two orders of magnitude more write traffic than today, when the busiest repositories see at most dozens of writes in a single second. The key observation is that Git objects are immutable and named by content, so writers can store packs in Blob Storage without coordination. Only the reference update needs agreement. That goes to Ref-CAS, a separate replicated log for refs and the pack manifest, where each update is a compare-and-swap committed by a quorum. Reads start with a version check, so an unchanged repository costs a single comparison, and replicas are disposable caches.

The post explains the two simpler layouts it rejected. One blob for all refs serializes writes, and the first prototype topped out in the mid-hundreds per second. Splitting refs across segment blobs lets writes scale but makes every read check every segment. In internal tests the system handled 7,200 pushes per second to one repository with 5,000 concurrent agents, and Ref-CAS runs at tens of thousands of reference transactions per second.

Read the limits too. Global replicas will serve reads only within a bounded staleness, and the bound isn't stated. Partial and shallow clones still have gaps, no latency or cost figures are given, and the system is in limited private preview with broader rollout planned for early next year. [source →](https://github.blog/engineering/architecture-optimization/inside-githubs-new-git-storage-architecture/)

## Cloudflare rebuilds only what the event touched, and escalates when unsure

Cloudflare's DNS Zone Builder now receives about 700 record changes per second, up from about 250 in 2022. A full build reads, encodes and compares every record in a zone and holds the zone in memory, and some zones exceed 20 million records. A planner now maps each event to one of five build types, and the targeted output must match what a full build would produce, byte for byte, for every key the plan owns. If it can't guarantee that, it escalates to a full build.

Over a 24-hour window, 92.95% of builds avoided a full-zone rebuild. Aggregate working-set memory fell from an average of 49 GiB to 7 GiB, and median build completion delay fell from about 7.7 seconds to about 3.3 seconds. The rollout is worth copying: equivalence tests, then a mirror builder fed by the production stream (a 0.31% diff rate across 234,313 matched zones), then a staged cutover by zone-name hash.

The post is explicit that the planner never turns uncertainty into less work. It is equally explicit about an exception: above a fixed record-count threshold the builder never escalates to a full build, accepting some risk on rare cases. Reported latency excludes distribution time through Quicksilver. [source →](https://blog.cloudflare.com/dns-targeted-zone-builds/)

## ClickHouse picks availability when every fence fails

Promoting a Postgres standby does not stop the old primary from accepting writes. The post walks through cases where withholding commit acknowledgements isn't enough, including quorum commit where the other standby's ack still lets the old primary commit. ClickHouse runs every fencing mechanism in parallel and proceeds on the first success. On AWS each server has a second network interface for clients and replication, and the fence is a forced detach of it. On GCP it is a single delete call on a Dynamic NIC, and on bare metal the VM's virtual interface is set down.

The author's AWS log shows fencing complete in about two seconds, and GCP trials saw the last packet on a user flow 0.7 to 2.5 seconds after the request. The weaker mechanisms have known holes: rewriting `pg_hba.conf` only affects new connections, and stopping Postgres is undone by a reboot.

If every fence fails, the standby promotes anyway. The author calls that a deliberate choice for availability, pinned by a test. A stricter design would page someone and leave no primary in the meantime. The timings are from the author's own trials, and the AWS example is a single log. [source →](https://clickhouse.com/blog/fencing-a-postgres-primary-that-might-still-be-alive)

## Meta separates the release unit from the execution unit

Meta's ads feature framework compiled every feature into one merged graph, and that graph was also what got released, so one bad feature blocked all of them. The framework grew from a few hundred features to more than 20,000. F3 Lightning compiles and releases each feature as its own configuration, ordered by a priority queue that weighs impact and risk. At service startup it builds one execution plan across the active features with shared nodes deduplicated, and a failed node marks only its downstream nodes not ready.

Per-request cost is kept down with a single memory buffer of slots and dense integer indexes in place of identifier lookups. Meta reports about 3.6x faster time to production for comparable extraction features with no increase in infrastructure compute cost. The early per-feature prototypes increased CPU usage because sharing between features was lost, and the startup planning was what restored parity.

The 3.6x figure applies only to comparable extraction features, model-related tests are expensive and run in a later stage, and no absolute latency or memory numbers are given. [source →](https://engineering.fb.com/2026/11/03/ml-applications/f3-lightning-how-meta-accelerates-ads-ml-features-to-production/)

## Anthropic on what agent memory costs to keep correct

Anthropic's post defines agent memory as knowledge kept between sessions as readable context, excluding weights, in-context learning and compaction. Its main mechanism is dreaming, an offline pass that reads transcripts, then rewrites or corrects notes, merges duplicates and promotes a small set into context injected at every session start. On CL-Bench 1.0's database task, memory raised Opus 5.5's mean reward from 0.655 to 0.838, but Sonnet 4.6 only from 0.330 to 0.364, and a refined instruction to read memory and test theories lifted that model to 0.641.

On a corpus of roughly 350,000 files, a dreamed wiki alone scored 48% of graded criteria, up from 13%, and wiki plus search scored 61% against 53% for search alone. In a contract-terms task, one page per contract kept 57 of 57 facts where a shared table kept 41.

The costs are stated: dreaming needs compute, a wrong injected note is carried into every session, and longer instruction files reduce adherence, so the top layer must stay small. Wikis showed no clear gain on a mostly single-document task, and the Pokémon runs are one run per model with no error bars. [source →](https://www.anthropic.com/research/components-of-agent-memory)
